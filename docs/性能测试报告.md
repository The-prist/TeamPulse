# TeamPulse 性能测试报告

> 日期：2026-10-27　环境：Windows 11 + Docker Desktop（WSL2），容器内 MySQL 8.0 + Spring Boot 3.2.4
> 工具：`tests/perf/load.mjs`（零依赖，Node 内置 fetch）
> 复现命令见文末。**本报告所有数字均来自实际执行。**

| 项 | 设置 |

## 二、结果一：不同端点的固定开销（20 并发 / 12s）

| 端点 | 成功 | 失败 | RPS | p50 | p95 | p99 | max |
|---|---|---|---|---|---|---|---|
| `/actuator/health`（无业务） | 2290 | 0 | 189.8 | **11.3ms** | 17.6ms | 21.6ms | 29.9ms |
| `/api/v1/attendance/my`（单表查询） | 2290 | 0 | 189.8 | **10.6ms** | 17.1ms | 21.4ms | 29.4ms |
| `/api/v1/attendance/records?size=1` | 2290 | 0 | 189.8 | **31.2ms** | 40.5ms | 45.7ms | 56.5ms |
| `/api/v1/attendance/records?size=200` | 2290 | 0 | 189.8 | **38.0ms** | 50.3ms | 58.0ms | 62.9ms |

**读法**：

- 框架底座（健康检查）≈ **11ms**，这是 Tomcat + Spring + JSON 的最小开销
- 打卡记录接口 ≈ 31ms，比底座多 **20ms**；从 `size=1` 到 `size=200`（200 倍数据量）只增加 **7ms**
  → **开销不在返回数据量，而在固定的查询与组装成本**
- 该接口每次要跑：`COUNT(*)` 分页总数 + 主查询 + 用户批量补全 + 设备批量补全，共 4 次数据库往返

## 三、结果二：加索引前后（同一批 5 万行数据）

`attendance_record` 原有索引里没有能覆盖「日期过滤 + 按打卡时间倒序」的组合，V8 新增 `(work_date, punch_time)`。

| 场景 | 执行计划 | SQL 层耗时（3 次取中位） |
|---|---|---|
| 加索引前：`WHERE work_date BETWEEN ? AND ? ORDER BY punch_time DESC LIMIT 20` | `key=idx_record_date_status`，**Using filesort** | 0.62ms |
| 加索引后（同一 SQL） | 仍 `idx_record_date_status` + filesort（原因见下） | 0.62ms |
| 强制走 `punch_time` 索引 | `key=idx_punch`，无 filesort | 0.39ms |
| 强制走 `punch_time` 索引 + work_date 过滤 | 无 filesort | 0.30ms |

**结论（重要且如实）**：

1. **数据库不是瓶颈**：最差 0.62ms，占接口 31ms 的 **2%**
2. **新增 `(work_date, punch_time)` 基本没改变这个查询的计划**：`work_date` 是**范围**条件，
   索引第二列无法消除 `ORDER BY punch_time`，MySQL 仍要 filesort
3. 想要真正消除 filesort，需要让**排序键同时是范围键**（例如直接按 `punch_time` 区间过滤），
   可省约 0.3ms（占比 1%）——收益远小于应用层优化的空间
4. 因此 V8 索引保留（对「按日期精确过滤 / 日历」类查询有用，且零风险），
   **但不宣称接口因此变快**

> 另外记一次「冷启动」测量：后端刚重启后立刻压测，同一接口 p50 达 **147ms**、p99 282ms。
> 原因是 JVM 未预热 + 容器刚起、CPU 争用。**首次压测必须预热**，否则数字会误导。

## 四、瓶颈定位与改进建议

| 观察 | 推断 | 建议 |
|---|---|---|
| 底座 11ms，记录接口 31ms | 固定开销 ≈ 20ms | 优先减数据库往返次数 |
| size 1→200 只增 7ms | 序列化不是主要成本 | 不必急着换序列化库 |
| 每次请求 4 次 DB 往返（count + 主查询 + 2 次批量补全） | `COUNT(*)` 与批量补全可合并/缓存 | ① 前端不需要精确总数时改为「不查 count」（`page.setSearchCount(false)`）② 用户/设备信息加短 TTL 缓存（Caffeine，5~10s） |
| RPS 约 190（20 并发，4 个路径各 190） | 单机单实例 ~700 req/s 量级 | 4C4G 单机对 20~200 人公司完全够用 |

**结论**：接口 p95 在 50ms 内，20 并发下无失败、无超时（超时阈值 20s），
对「200 人规模、每日数百次打卡」的负载有非常充分的余量。

## 五、复现步骤

```bash
# 1) 起容器栈
docker compose up -d

# 2) 灌 5 万条压测数据（仅测试环境）
docker exec -i tp-mysql mysql -uroot -p<密码> teampulse < tests/perf/seed-perf-data.sql

# 3) 跑压测（会自动登录拿 token）
node tests/perf/load.mjs \
  --base http://127.0.0.1 \
  --admin-password <管理员密码> \
  --path '/api/v1/attendance/records?page=1&size=20' \
  --path '/api/v1/attendance/calendar?from=2026-05-01&to=2026-10-27' \
  --concurrency 20 --duration 15 --warmup 3 \
  --json perf-result.json

# 4) 清理压测数据
docker exec tp-mysql mysql -uroot -p<密码> teampulse \
  -e "DELETE FROM attendance_record WHERE employee_no LIKE 'P%'"
```
