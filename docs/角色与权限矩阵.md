# TeamPulse 角色与权限说明

> 本文档对应后端迁移 `V4__init_rbac_department.sql` / `V5__fix_auditor_permissions.sql`，
> 代码落点：`com.teampulse.module.rbac`、`com.teampulse.security`。

## 一、为什么这么设计

原来的权限模型只有两个硬编码角色（`admin` / `member`），18 个接口统一写
`@PreAuthorize("hasRole('ADMIN')")`。问题有三个：

1. **一个人干四种活**：系统管理员同时是 HR、行政、审计，职责冲突（HR 定规则又能改自己的考勤）。
2. **加角色必须改代码**：想多一个「部门经理」得改注解、重新编译。
3. **没有数据边界**：部门经理要么看全公司，要么什么都看不到。

现在改成 **RBAC + 部门 + 数据范围 + 审批流**：

| 能力 | 实现 |
|---|---|
| 角色 | `role` 表，6 个内置角色，`data_scope` 决定数据范围 |
| 权限点 | `permission` 表 + `role_permission` 关联，接口用 `hasAuthority('module:action')` |
| 组织 | `department` 树形表 + `user.department_id` / `team.department_id` |
| 数据范围 | 角色上的 `ALL` / `DEPT` / `SELF`，由 `DataScopeService` 解析 |
| 审批 | `makeup_request` 表：员工申请 → 主管/HR 审批 → 通过才写考勤 |

关键取舍：**权限点放数据库、数据范围放角色**。加一个角色只需插数据；
加一个接口只需加一行 `@PreAuthorize` + 一条权限点。

## 二、六个角色

| 角色标识 | 名称 | 数据范围 | 权限数 | 典型职责 |
|---|---|---|---|---|
| `sysadmin` | 系统管理员 | ALL | 22（全部） | 账号、权限、设备、系统配置；不做业务审批 |
| `hr` | 人事专员 | ALL | 12 | 考勤规则、补卡审批、考勤报表、员工档案只读 |
| `manager` | 部门经理 | DEPT | 14 | 本部门团队/日程/看板/日志 + 考勤异常审批 |
| `leader` | 团队负责人 | DEPT | 8 | 本部门协作与日程管理，不含审批 |
| `employee` | 普通员工 | SELF | 6 | 自己的日程、看板、日志、考勤 + 提补卡申请 |
| `auditor` | 审计专员 | ALL | 10 | 全公司只读，用于合规核查 |

## 五、数据范围怎么生效

`DataScopeService` 读取当前角色 `data_scope`，返回 `DataScope` 对象：

| data_scope | 解析结果 | 落到 SQL |
|---|---|---|
| ALL | 不限制 | 不加条件 |
| DEPT | 本部门所有 userId 集合 | `creator_id IN (...)` / `user_id IN (...)` |
| SELF | 只有自己 | `creator_id = me` |

已接入的接口：

| 接口 | 过滤字段 |
|---|---|
| `GET /schedule` | `creator_id` |
| `GET /worklog` | `creator_id` |
| `GET /attendance/records` | `user_id` |
| `GET /user/list` | `department_id`（DEPT）/ `user_id`（SELF） |
| `GET /team/list` | `department_id`（DEPT）/ 成员子查询（SELF） |
| `GET /makeup/pending` | 申请人 `user_id` |

实测效果（同一批数据）：

| 登录人 | 角色 | 能看到日程 | 能看到打卡 |
|---|---|---|---|
| admin | sysadmin(ALL) | 11 条 | 84 条 |
| zhangsan | manager(DEPT) | **4 条**（只有研发部） | **56 条**（研发部 4 人） |
| lisi | employee(SELF) | **1 条**（只有自己） | **14 条**（只有自己） |
| zhaoliu | auditor(ALL) | 11 条 | 84 条 |

## 六、补卡审批流程

```
员工                  后端                        主管/HR
 │  POST /makeup       │                            │
 ├────────────────────►│ 校验：有工号、非未来时间、无重复待审 │
 │                     │ 写 makeup_request(pending)  │
 │                     │                            │
 │                     │  GET /makeup/pending  ◄─────┤ 按数据范围过滤
 │                     │                            │
 │                     │  POST /makeup/{id}/review ──┤ approved=true/false
 │                     │                            │
 │                     │ 通过 → 复用 manualPunch     │
 │                     │ 生成 attendance_record      │
 │                     │ 重建 attendance_daily       │
 │  GET /makeup/mine   │                            │
 ◄─────────────────────┤ 状态 approved + recordId    │
```

约束与校验：

- 没有工号的账号不能申请（`BAD_REQUEST`）
- 不能为未来时间申请
- 同一时间点不能有两条待审批申请（`CONFLICT`）
- 只有 `attendance:approve` 能审批，且申请人必须在审批人数据范围内（否则 `FORBIDDEN`）
- 已处理的申请不能重复审批（`CONFLICT`）
- 通过后生成的记录 `source=MANUAL`，备注写明「补卡审批通过 #单号」，保证可回溯

## 九、已知限制（后续可做）

1. **一人一岗**：`user.role` 只存一个角色；真实企业存在一人多岗，需要 `user_role` 中间表。
2. **部门只有一层生效**：`DEPT` 范围只统计本部门，未包含子部门（`department.parent_id` 已预留）。
3. **团队级范围未细分**：`team_role = leader` 目前等同 DEPT，不能只看"我带的团队"。
4. **权限点不能在线配置**：角色权限改动需要写 SQL；没有管理界面。
5. ~~无操作审计日志~~ **已实现**：`audit_log` 表 + `@Audited` 切面覆盖 20 个写操作（见第十节）。

## 十、审计日志（audit:view 已落地）

`audit:view` 原本只是预留权限，现在已经对应到真实功能。

| 项 | 内容 |
|---|---|
| 数据表 | `audit_log`（迁移 V6）：只追加，**无 `updated_at` / `deleted`**，不可修改 |
| 记录方式 | `@Audited(module, action, detail)` 注解 + `AuditLogAspect` 切面，业务代码零侵入 |
| 记录字段 | 操作人昵称与角色**快照**、动作、资源与资源 id、结果、耗时、IP、User-Agent、traceId |
| 埋点范围 | 20 个写操作：用户 4 / 团队 5 / 考勤 3（含审批）/ 设备 4 / 敏感词 3 / 评论 1 |
| 失败留痕 | 业务异常穿过切面时先记 `FAILURE` 与错误信息，再原样抛出 |
| 查询接口 | `GET /api/v1/audit`（操作人/模块/动作/结果/时间区间/traceId）、`/{id}`、`/options` |
| 界面 | 管理后台「系统 → 审计日志」，菜单按 `audit:view` 显示 |
| 需求编号 | `FR-AU-01` 操作留痕 / `FR-AU-02` 失败也留痕 / `FR-AU-03` 审计查询 |

### 谁能看审计

| 角色 | 可见 | 说明 |
|---|---|---|
| sysadmin 系统管理员 | ✅ | 全部 |
| hr 人事专员 | ✅ | 全部（含自己被审计的记录，已在需求规格中说明） |
| auditor 审计专员 | ✅ | 全部 |
| manager / leader / employee | ❌ | 接口返回 403，前端菜单也不显示 |

### 与 traceId 的关系

审计记录的 `trace_id` 与 `X-Trace-Id` 响应头、`logs/teampulse.log` 里的 `[traceId]` 是同一个值，
所以「页面报错 → 日志定位 → 谁干的」可以一路对上。
